- 不给服务维度/集群维度做**独立评分**——题目要求的是「统计」，新增评分模型是引入新算法。
- 不引入机房 / 可用区 / k8s 集群等第三种粒度。
- 不改动规则引擎、评分模型、AI 归因链路的任何现有逻辑；统计是**只读聚合**。
- 不做前端。

## 三、A：多粒度巡检统计

### A1 配置层：引入集群分组

`config/services.yaml` 新增顶层 `clusters`（键 → 展示名），每个服务新增可选字段 `cluster`：

```yaml
clusters:
  trade: 交易集群
  payment: 支付集群
  supply: 供应链集群
  user: 用户集群
  external: 外部依赖集群

services:
  gateway:
    cluster: trade
    ...
```

**校验规则**（沿用项目「配置写错直接启动失败」的风格）：
- `services.<name>.cluster` 若填写，必须出现在 `clusters` 中，否则启动期抛 `ConfigError`——拼错一个字母就会把一个服务静默分错组，这类错误必须在启动时暴露。
- 未填写 → 归入保留键 `default`，展示名「未分组」。
- `clusters` 允许为空（全部归入 default）。

改动点：`config/schemas.py`（`ServicesConfig.clusters`、`ServiceSpec.cluster`、`to_topology` 传递 + 校验）、`config/services.yaml`、`staguard/models/topology.py`（`ServiceNode.cluster`、`Topology.cluster_of/cluster_label/cluster_members/cluster_labels`）。

### A2 数据模型

新增 `staguard/models/statistics.py`：

```python
class ServiceStat(BaseModel):
    service: str
    cluster: str                 # 集群键
    cluster_label: str           # 展示名
    tier: str | None
    owner: str | None
    criticality: float
    anomaly_count: int           # 未抑制异常条数
    max_level: Severity | None   # 最严重级别；无异常为 None
    affected_instances: list[str]
    total_instances: int
    worst_metric: str | None     # 最严重异常所在指标（中文名）
    worst_summary: str | None    # 「实测 99.0% / 基线 55.0%，P1 紧急」一句话
    rule_ids: list[str]          # 命中的规则 ID（去重、有序）
    root_cause_of: list[str]     # 该服务作为主根因的簇 ID
    in_clusters: list[str]       # 该服务作为成员出现的簇 ID

    @property affected_ratio -> float | None   # 受影响实例占比，0 实例时为 None
    @property is_healthy -> bool               # anomaly_count == 0

class ClusterStat(BaseModel):
    cluster: str
    label: str
    service_count: int
    affected_service_count: int
    anomaly_count: int
    max_level: Severity | None
    affected_instances: int
    total_instances: int
    root_cause_count: int        # 该集群内服务作为主根因的簇数

    @property affected_ratio -> float | None
    @property affected_service_ratio -> float | None
```

挂到 `InspectionReport`：
```python
service_stats: list[ServiceStat] = Field(default_factory=list)
cluster_stats: list[ClusterStat] = Field(default_factory=list)
```
`models/__init__.py` 导出，`InspectionReport.model_dump()` 自动带出 → JSON（CLI `--json` / API `?format=json`）与落库 payload 都无需另写序列化。

### A3 计算

新增 `staguard/detect/statistics.py`（聚合层，与去重/聚类同包）：

```python
def build_service_stats(ctx, anomalies, clusters) -> list[ServiceStat]
def build_cluster_stats(ctx, service_stats) -> list[ClusterStat]
def build_granularity_stats(ctx, anomalies, clusters) -> tuple[list[ServiceStat], list[ClusterStat]]
```

口径（必须写进文档，避免读者自行解读）：
1. **只统计未抑制异常**（`not anomaly.is_suppressed`）。被抑制项与代表它的那条同服务同指标，计入会导致同一问题被数两次。
2. 服务维度**覆盖全部服务**（含 `ctx.all_services()` 里的外部依赖），无异常的服务 `anomaly_count=0`、`max_level=None`——「哪些服务是干净的」本身就是统计要回答的问题。
3. `max_level` 取未抑制异常的**最高级别**（`Severity` 是 IntEnum，P1 数值最小，用 `min`）。
4. `affected_instances` 去重后按字典序；`total_instances` 取拓扑里的实例数。
5. 排序：服务维度 `(max_level or 5, -anomaly_count, service)`；集群维度 `(max_level or 5, -anomaly_count, cluster)` —— 有异常的排在前面，同级按异常数降序。
6. `root_cause_of` / `in_clusters` 来自 `clusters[].primary.service` 与 `clusters[].services`。

## 五、C：口径显式化

均只改渲染层，不动计算：

1. **评分来源**（Markdown 评分卡下方）：
   - AI 非降级且 `ai_adjust == 0` → `> 评分为规则算分（可解释扣分明细见上表），AI 未调整分数。`
   - AI 降级 → `> AI 降级运行（{原因}），评分完全由规则算出，未经模型调整。`
   - 已有分支（`ai_adjust != 0`）保持原样。
2. **归因覆盖口径**（Markdown 「根因分析」章节开头）：
   `> 本次 {N} 条未抑制异常全部归入 {M} 个根因簇，逐簇给出根因；另有 {K} 条被抑制异常不单独归因（见异常清单折叠区）。`

## 七、实施中暴露的额外缺陷（已修）

1. **影响面算出 133%**：链路健康度（BIZ-06）把链路上最弱节点的*服务名*放进了 `instance` 字段，
   直接计数会把 8 个受影响实例数到 6 个实例的集群里去。修法：分子只认拓扑里声明过的实例名，
   分母取配置声明的实例清单；链路级异常仍计入异常数，但不占实例影响面。
   （这是「统计口径必须先定死」的又一个例子——数字算错时报告看起来完全正常。）
2. **`sample` 命令的提示误报**：即使本次刚成功导出 `-llm` 版本，只要目录里存在
   `-rule-fallback` 文件就会提示「配置 key 后重跑」。改为按**本次导出实际走的模式**判断。
3. **`docs/samples/AI对比说明.md` 的量化数字过期**：影响面描述长度原写 27~101 / 93~226 字，
   实测为 57~141 / 207~471 字；耗时区间 5.7~9.0s → 5.9~9.7s。已按本次 7 份报告重新测量并补上口径说明。
