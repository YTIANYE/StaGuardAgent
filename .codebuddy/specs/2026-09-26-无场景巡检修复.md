## 一、问题

**现象**：不带 `scenario_id` 的巡检全部拿不到数据。实测三种部署形态全中：

| 入口 | 参数 | 实测 |
| --- | --- | --- |
| `staguard run` | 不带 `--scenario` | 状态 失败 / 评分 0.0 / 异常 0 条 |
| `make schedule` | `schedule --interval 30` | 每轮都失败 |
| `docker-compose.yml` scheduler | `schedule --interval 30 --source http` | 同样失败 |
| `deploy/k8s/30-cronjob.yaml` | `args: ["run", "--source", "http"]` | 同样失败 |

**根因**：`orchestrator.py:146` 的 `detect_dataset = scenario_id or run_id` 一个变量身兼两职：

1. **取数用**——它被塞进 `CollectRequest.dataset_id`，数据源按「数据集 ID」取数；
2. **入库 / 规则读取用**——标准化后的点写进这个数据集，规则再从它读。

不带场景时这个 ID 是 `run-20260925-100000`，文件源里没有这个文件、模拟接口返回 404，
于是采集 0 条 → `_finish_without_data`。**「不带场景 = 巡检当前状态」这层语义只写在
`api.py:108` 的接口说明里，数据源层面从未实现。**

**被动暴露的三个次生问题**：

1. `report/console.py:159` 在异常为空时无条件打印绿色面板
   「未发现越线异常，各指标处于历史同时段正常区间」——把「一点数据都没拿到」
   说成「体检全绿」。同一次运行的评分面板却诚实写着 `0.0 / 100 无法评估`，两句自相矛盾。
   **静默失败伪装成正常，比直接报错更危险。**
2. `_finish_without_data` 直接 return，**不写 Markdown 报告**，磁盘与报告接口都没有留痕。
3. `scheduler.py` 的启动日志写「场景 全部」，与实际的「不指定场景」不符。

## 二、方案

把「取数用的数据集」与「入库用的检测数据集」拆成两个概念：

```python
source_dataset  = scenario_id or settings.app.live_dataset   # 取数
detect_dataset  = scenario_id or run_id                      # 入库 + 规则读取
```

- `scenario_id` 退回它本来的职责：**回放某个历史故障切片**；
- 不带场景时，从「代表当前水位的数据切片」取数——模拟环境下由新配置项
  `live_dataset` 指定（默认 `S0`，即正常态切片）；真实环境接实时数据源后，
  数据源按 `window` 查实时数据，这一项不生效；
- `detect_dataset` 保持 `run_id`：**两者不能合并**。合并后每次定时巡检都往同一个
  数据集写检测数据，下一次巡检会读到上一次的残留，数据互相污染且失效方式静默。

## 三、明确不做

- 不新增数据集、不改变数据生成量与 db 体积（复用已有切片，默认 S0）；
- 不做「文件源按窗口从多个数据集拼数据」——多个场景切片窗口相同，拼出来是无意义的混合水位；
- 不改规则引擎、评分模型、AI 归因链路；
- 不把失败粉饰成成功（本次修改的方向恰好相反）。

## 六、实施中暴露的额外缺陷（已修）

1. **复发识别把「同一个窗口的不同切片」当成复发**。`recent_clusters` 原来按
   `(scenario_id, window_end)` 排除同窗口历史；不带场景的巡检与同名场景巡检读的是同一份数据，
   却因 `scenario_id` 不同而互相进入对方的历史。修法：判据退回到**窗口本身**——
   复发意味着「同类问题在之后的窗口里又出现」，同一个窗口被反复看都不算复发。
2. **模型可以自行声明 `is_recurring`**。历史检索已经算出这个事实（`_mark_recurrence`），
   但 LLM 路径直接采信模型的字段。实测 S6 在一个没有任何历史同类事件的场景里被写成
   「历史复发，说明上次的处置并未根治」。修法：校验阶段用检索结果校正模型的声明
   （`_sync_recurrence`）并记录一次修复——和「评分由规则算」同一个道理。
3. **孤立簇行会冒充历史**。表结构漂移自愈会重建单张表，重建 `runs` 之后 `clusters` 里
   留下没有 run 记录的孤立行；它们没有窗口、没有切片，却能被签名匹配上，
   于是「恢复出厂设置后的第一份报告」就写着历史复发。修法：历史检索只认有 run 记录的簇。
4. 连带的文档数字更正：`docs/05` 的库体积与巡检耗时按实测重写
   （230 万点 / 约 420MB / 单次巡检约 7 秒），`gen-data` 汇总行的体积改为**含 WAL**统计
   （只算主库会把 416MB 报成 112MB）。

## 七、复核全量测试时发现的性能问题（已修）

- **现象**：`make test` 从 2 分半变成 **15 分 41 秒**；单次巡检从约 5 秒变成 **46 秒**，
  慢的全部落在「动态基线」阶段（40.9s / 40952ms）。
- **根因**：`metric_points` 有两百多万行，但库里**没有查询计划统计信息**（`sqlite_stat1`）。
  没有统计信息时 SQLite 按「表很小、分布均匀」的默认猜测选计划，
  把「按序列取 14 天历史」的查询选成了按 `(dataset_id, ts_epoch)` 全数据集扫描再逐行过滤
  （150 条序列 × 60 万行）。有统计信息后规划器改走
  `ix_mp_series(dataset_id, metric, service, instance, ts_epoch)`，该阶段回到 1.5 秒。
- **为什么难发现**：结果完全正确、日志里没有任何异常、阶段状态全是「成功」，
  只有耗时不对。属于「静默的性能故障」。
- **修法**：`Database.optimize()`——统计信息缺失时对该表 `ANALYZE`，
  已有统计信息时用 `PRAGMA optimize`；挂在 `build_all`（生成数据集之后）
  与数据集被整体重写的 store 阶段。另加回归测试
  `test_metric_points_has_planner_stats` 锁住它。
- **效果**：单次巡检 46s → 7.3s；全量测试 941s → **154s**（86 passed / 1 skipped）。
- 连带：14 份样例在修复前导出，耗时数字被污染（45~53s），已在修复后重新导出
  （规则兜底 5.2s / 大模型 12.1s）。
