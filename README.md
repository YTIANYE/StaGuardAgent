# StaGuardAgent

> AI 驱动的业务稳定性自动化巡检 Agent
> 全自动定时巡检 · 多维度规则引擎 · AI 根因归因 · 标准化巡检报告

---

## 一句话说明它解决什么问题

传统巡检靠人定时核对接口成功率、延时、报错、资源负载，问题是**滞后、漏检、无法归因、没有标准报告**。
StaGuardAgent 把这条链路自动化，并且**重点解决两个人工巡检做不到的事**：

1. **动态基线代替固定阈值** —— 固定阈值在凌晨必然误报、在晚高峰必然漏报，因为业务流量本身有周期；
2. **根因归因代替异常罗列** —— 把「网关、订单、支付、银行渠道同时报警」收敛成
   「根因在银行渠道，其余三个是被传导上来的影响面」，并给出分档处置建议。

## 快速开始

```bash
# 1. 安装依赖（Python 3.11+）
make install                     # 或 pip install -e ".[dev]"

# 2. 生成模拟数据集：14 天归档历史 + 7 个故障场景（约 15 秒）
make gen-data

# 3. 跑一次巡检（不配 LLM 也能跑，会自动降级为规则归因）
make run SCENARIO=S1

# 4. 看报告
cat reports/S1/run-*.md
```

想接真实大模型，把 key 填进 `.env` 即可（参考 `.env.example`）：

```bash
cp .env.example .env
# 编辑 .env，填入 STAGUARD_LLM_API_KEY=sk-xxxx
make run SCENARIO=S1
```

## 项目结构

```
staguard/
├── models/        领域模型（指标、异常、基线、评分、AI 结论）
├── config/        配置体系（环境变量 + 4 份 YAML 策略文件）
├── dataset/       模拟数据集：场景生成器、归档同步、文件数据集
├── collector/     数据接入：本地结构化文件 / 模拟 HTTP 监控接口
├── normalize/     标准化清洗：单位统一、越界剔除、时间对齐、缺失处理
├── store/         结构化存储（SQLAlchemy Core，SQLite / PostgreSQL 可切换）
├── rules/         规则引擎：16 条规则 + 动态基线 + 分级
├── detect/        异常聚合去重 + 拓扑传播根因聚类
├── ai/            证据包 → 大模型归因 → 校验 → 三级降级
├── report/        控制台 / Markdown / JSON 报告 + 历史对比
├── notify/        告警推送（钉钉 / 企微，默认 dry-run）
├── orchestrator.py 巡检编排（10 个阶段，阶段隔离 + 全程留痕）
├── scoring.py     稳定性评分模型
├── scheduler.py   定时调度
├── api.py         HTTP 服务（健康探针 / 手动触发 / 报告导出）
├── mockapi/       模拟监控数据接口
└── cli.py         命令行入口
config/            巡检策略：服务拓扑、阈值、规则、评分、场景（全部可配）
data/              模拟数据集与变更事件
deploy/k8s/        K8s 部署清单（Deployment + CronJob + HPA）
docs/              设计文档、规则设计、AI 集成方案、数据结构
tests/             单元测试（毫秒级）+ 端到端测试
```

## 核心能力

| 能力 | 实现要点 |
| --- | --- |
| 数据源接入 | 双通道：本地结构化文件 + 模拟 HTTP 监控接口，**共用同一份底层数据**，结果必然一致 |
| 规则引擎 | 16 条规则覆盖业务层 / 性能层 / 资源层 / 链路层；阈值按服务红线自动缩放 |
| 动态阈值 | hour-of-week 稳健基线（中位数 ± 4 × 1.4826 × MAD），样本不足自动回退静态阈值并标注 |
| 异常分级 | 紧急 / 严重 / 一般 / 轻微，判定条件全部可在 YAML 调整；持续时长沿时间轴精确计算 |
| 根因聚类 | 按依赖拓扑聚合异常，加权选取主根因（信号性质 / 严重度 / 传播方向 / 时序） |
| AI 归因 | 证据包（只有事实）→ 强 schema 校验 → 三级降级；AI 只做归因与 ±5 分微调 |
| 评分模型 | 可用性 40 + 性能 25 + 资源 20 + 稳定性 15，可解释扣分明细 + 封顶规则 |
| 报告 | 控制台结构化输出 + 七章 Markdown 报告 + JSON，支持多次巡检对比与复发识别 |
| 工程化 | 阶段隔离、结构化日志、幂等建表、容器化、K8s 清单、54 项测试 |

## 设计取舍（面试里最常被追问的几条）

**1. 分数由规则算，AI 只能微调 ±5**
同一份数据必须得到同一个分数，否则「多次巡检对比」毫无意义。
AI 负责归因和给建议（它的强项），不负责打分（需要一致性的活）。

**2. AI 挂了报告照样出得来**
三级降级：大模型 → 规则决策树 → 纯统计。
金融场景里「因为 AI 挂了所以今天不出巡检报告」是不可接受的。
降级会如实写进报告的 AI 元信息里。

**3. 证据包只放事实，不放结论**
如果把规则的分级结论也喂给模型，它会倾向于复述它，归因就退化成「把规则输出翻译成人话」。
拿走结论、只留证据，模型才被迫真的做一次因果推理。

**4. 故障数据不能污染自己的基线**
长期归档（14 天，干净）与场景数据（含注入）分开存储。
历史样本里混着故障点时，均值会被带偏、MAD 不会——这是动态阈值能不能用的分水岭。

**5. 采集范围由规则反推**
内存泄漏这类慢故障需要 24 小时观察窗。如果按固定的 30 分钟窗口采集，
规则写得再好也无从判定，而且失效方式是完全静默的。

## 报告示例

`make run SCENARIO=S1` 后可在 `reports/S1/` 下看到完整 Markdown 报告，包含七个章节：
巡检概览（评分卡 + 扣分明细）、风险总结、异常清单、根因分析（含传播路径与证据引用）、
修复建议（立即止血 / 短期加固 / 长期治理）、稳定性趋势（与上次对比 + 复发识别）、附录。

已生成的样例见 [`docs/samples/`](docs/samples/)（`make sample` 可重新导出）。
其中**规则兜底版与真实大模型版并存**，两者的归因质量差异见
[`docs/samples/AI对比说明.md`](docs/samples/AI对比说明.md)——那份文档同时记录了
接入真实模型过程中暴露并修掉的 7 个缺陷。
