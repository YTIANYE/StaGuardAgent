| --- | --- | --- | --- |

## 二、动态基线（动态阈值加分项的实现）

### 算法

```
样本池：归档数据集中「同星期几 + 同小时」的全部历史点（±1 小时槽兜底）
基线：  median ± k × 1.4826 × MAD      （k = 4）
下限：  max(1.4826 × MAD, 0.8% × |median|)
```

### 三个取舍点

**1. 为什么按 hour-of-week 取样**
业务有两层周期叠加：一天内的双峰（午间 + 晚间）和一周内的周效应（周末流量低）。
只按小时取样会把周一 10 点和周日 10 点混在一起，基线被周效应污染。
按「星期几 + 小时」取样，两层周期同时被消掉。

**2. 为什么用中位数 + MAD 而不是均值 + 标准差**
基线样本里必然混着历史故障点。均值会被离群点带偏——
一次大故障就能把阈值永久抬高，此后同类故障全部漏报，而且失效是静默的。
MAD 的崩坏点是 50%，稳得多。

实测：190 个正常点（100~104）+ 10 个故障点（3000）时，
中位数口径的基线仍在 102 附近，均值已被拉到 240 以上。

**3. 为什么要有相对下限**
极稳定的指标（如成功率）MAD 会趋近于 0，
此时 0.01 的抖动会被算成几十个标准差。`0.8% × |median|` 的下限用来防止零尺度爆炸。

### 冷启动回退

样本量 < 30 或 MAD = 0 时，回退到 `thresholds.yaml` 的静态红线，
并在 `Baseline.mode` 上标记 `static_fallback`。

**回退必须可见**：报告里会显示「动态基线覆盖率」，
读报告的人必须能分清「这是和历史比出来的」与「这是拿固定红线卡出来的」——
两者的可信度完全不同。

### 阈值按服务自动缩放

同一套绝对标准要求所有服务，必然是一边误报一边漏报：

| 服务 | P99 红线 | 理由 |
| --- | --- | --- |
| gateway | 500ms | 入口抖动会直接放大到用户侧 |
| order-svc | 900ms | 核心交易链路 |
| payment-svc | 1200ms | 要等银行渠道，天然更慢 |
| bank-channel | 1500ms | 外部依赖，只有抖动没有优化空间 |

规则里的分级阈值按「默认红线尺度」书写，运行时按 `服务红线 / 默认红线` 等比缩放。
于是「网关 P99 超 500ms 算异常」和「银行渠道 P99 超 1500ms 才算异常」
用同一段配置就能同时成立，**规则本身一行都不用改**。

## 三、分级模型

### 判定流程

```
1. 取时序 → 取基线 → 计算偏离（deviation_pct / z_score / 倍数 …）
2. 按配置顺序（P1 → P4）匹配级别，首个全部条件满足者生效
3. duration_minutes 不是预先算好的值，而是**针对当前级别自己的条件**
   沿时间轴数出最长连续满足的时长，再与阈值比较
4. 回填真实的持续时长与起始时刻
5. 计算幅度分数
```

### 为什么持续时长要按级别分别计算

P1 要求「跌幅超 5 个百分点且持续 3 分钟」，P2 只要求「超 2 个百分点且持续 2 分钟」。
如果用同一个全局 duration，1 分钟的极端下跌会被误判成 P1——它其实只是瞬时毛刺。

实现上把每个条件键编译成一个逐点谓词，沿时间轴统计最长连续命中区间。
`value`、`drop_points`、`multiplier`、`z_score` 等可以逐点求值；
`cv`、`ratio`、`slope` 是窗口聚合量，无法逐点判断，其持续时长按整个窗口计。

### 条件键一览

| 键 | 语义 |
| --- | --- |
| `value` | 观测值（窗口内最坏值）越过阈值 |
| `deviation_pct` | 相对动态基线的百分比偏离（取绝对值比较） |
| `z_score` | 稳健 Z 分数 `|(v − median) / (1.4826 × MAD)|` |
| `drop_points` / `rise_points` | 绝对下跌 / 上升量（百分点），用于比率型指标 |
| `down_pct` | 相对基线的下降百分比 |
| `multiplier` | 相对基线的倍数 |
| `cv` | 窗口内变异系数（响应抖动） |
| `ratio` / `ratio_rise_pct` | 派生比值及其相对基线的涨幅 |
| `slope_pct_per_hour` | 每小时变化百分比（趋势型） |
| `below_slo` | 观测值跌破服务 SLO |
| `min_absolute` | 绝对量门槛，低基数不报 |
| `duration_minutes` | 需持续满足的最短时长 |
| `instances` | 同时受影响的实例数 |

**启动期强校验**：配置里出现未知条件键会直接让进程启动失败。
这类错误如果等到运行时才发现，表现是「规则静默不报警」——最难排查的一类故障。

### 严重度归一化（deviation_score）

不同量纲的异常必须可比，才能在一张表里排序、按严重度加权算分：

```
deviation_score = 0.55 × 幅度 + 0.20 × 持续时长 + 0.15 × 影响面 + 0.10 × 服务关键度
```

- **幅度**：用「该条件在配置里最宽松阈值 → 最严格阈值」作为 0~1 的映射区间，
  于是成功率的百分点、延时的毫秒数、QPS 的倍数、抖动的 CV 全部可比。
  阈值改了，幅度区间自动跟着改，不会过时；
- **持续时长**在 15 分钟处饱和——再长也不额外加权，否则一次长时间故障会把分数吃满，
  掩盖掉其它同时发生的更严重问题；
- **影响面**是同服务内被同一规则命中的实例占比，只能在所有规则跑完后回填。

### 级别与幅度的边界（重要）

**级别决定量级，幅度只在该量级内排序。**

典型冲突：CPU 从 47% 涨到 80%，绝对水位没到 85% 红线所以只判 P4，
但相对基线涨了 70%、z 分数几十。若按纯幅度算会得到满分 1.0，
于是一个 P4 的排序权重压过了 P1。

解决办法是把原始幅度压进该级别的区间内：

| 级别 | 幅度区间 |
| --- | --- |
| P1 紧急 | 0.75 ~ 1.00 |
| P2 严重 | 0.55 ~ 0.84 |
| P3 一般 | 0.35 ~ 0.64 |
| P4 轻微 | 0.15 ~ 0.40 |

这样「刚好踩线的 P1」永远排在「爆表的 P4」前面，与人工分级时的直觉一致。

### 趋势型规则的额外闸门

PERF-05 与 RES-03 强制要求**统计显著性**：

```
|t 统计量| ≥ 3.0 且 R² ≥ 0.5（内存趋势为 0.6）
```

原因：30 个点的噪声序列随手算出来的斜率很容易「看着」有 15%/h 的涨幅，
但 t 统计量往往只有 1 出头。没有这道闸门，趋势规则在干净数据上会稳定误报——
这是动态阈值落地最容易翻车的地方。

## 四、异常聚合

### 去重

`dedup_key = (rule_id, service, instance, metric)`。
一条规则在一个窗口内可能命中几十次（每分钟一次），
运维要看的是「订单服务成功率下跌，持续 23 分钟」，不是 23 条一样的记录。

### 抑制

同一 `(service, instance, metric)` 上，低级别异常让位于更严重的那条。
P99 超时的 P1 已经说明问题，再报一条「抖动偏高」的 P3 只会稀释注意力。
被抑制的异常仍会落库，在报告的折叠区里可见。

### 影响面回填

异常的影响面天然是聚合量——「3 个实例全部中招」和「只有 1 个」是性质不同的两件事。
所以它只能在所有规则跑完之后回填，再据此重算 `deviation_score`。

## 五、根因聚类

### 聚簇规则

1. 同一服务上的异常必在同一簇；
2. 两个服务若在依赖拓扑上互为上下游，其异常进同一簇。

### 主根因选取

**第一层：先比严重度。** 取本次异常里级别最高的那条，同级之间才进入加权打分。

这一步是实测踩坑后补上的，不能省：S4 场景里用户服务发布后业务错误率飙到 5.4%（P2），
同时入口网关因为流量天然波动有一条「成功率略低于 SLO」的轻微偏移（P4）。
早期实现直接用加权分数取最大值，结果那条 P4 在「越靠上游越像根因」这一项上拿满方向分，
**压过了真正出故障的 P2，把根因定位到了完全无辜的网关上**。

严重度优先在直觉上也更站得住：一个 P4 级的噪声解释不了下游的 P2 故障；
而最严重的那个异常，本身就是最值得优先解释的对象。

**第二层：同级之间按四个信号加权。**

```
score = 0.40 × 信号性质 + 0.25 × 严重度 + 0.20 × 方向 + 0.15 × 时序

信号性质：资源 1.00 / 性能 0.70 / 业务 0.30 / 链路 0.20   ← 这条异常本身有多像「原因」
方向    ：瓶颈类越靠下游越像根因（下游慢拖垮上游）
          症状类越靠上游越像根因（入口最先看到影响）
时序    ：最先出现症状的那条更接近源头
```

**三条硬规则**：

- **链路健康度（BIZ-06）永远不能当主根因**。它是对整条链路的概括
  （「网关到银行渠道的链路健康度 71%」），真正的原因必然落在某个具体节点上；
  让它当主根因，结论会退化成「网关有问题」这种没法落地的说法；
- **存在流量类异常时，主根因只在流量异常中选取**。
  全链路流量同向变化时根因在入口，把某台数据库的 CPU 高当根因是南辕北辙；
- **用异常自身的性质，而不是它所在服务的最强信号**。
  拿服务维度的最大值会系统性地偏向异常条数多的服务——
  而条数多恰恰说明它是被影响的那一方。

### 规则假设与 AI 结论并置

聚类会输出一段 `hypothesis`（传播假设），它与 AI 的结论**并列展示**。
两者不一致时报告会显式标注 `⚠️ 根因定位分歧`。

这不是容错设计，而是**刻意的交叉验证**：本次开发中，规则兜底「对着无下游的
银行渠道说它的下游依赖退化」这个缺陷，正是靠大模型给出不同结论才被发现的。
**两条独立路径的分歧点，就是缺陷藏身的地方。**

### 规则假设

聚类会输出一段 `hypothesis`（传播假设），它与 AI 的结论**并列展示**。
两者不一致时报告会标注 `⚠️ 与规则假设不一致`——
这种分歧恰恰是最值得人工看一眼的地方，把它藏起来等于丢掉了一次发现问题的机会。

## 六、多粒度统计

报告第四章给出两张统计表（实现：`staguard/detect/statistics.py`）：

| 维度 | 一行代表 | 关键列 |
| --- | --- | --- |
| 服务维度 | 一个服务，**含无异常的服务** | 异常数、最严重级别、受影响实例 / 实例总数、命中规则、最严重指标 |
| 集群维度 | `services.yaml` 里定义的一个集群 | 服务数、异常服务数、异常数、最严重级别、受影响实例、根因簇数 |

### 三条口径

**1. 只统计未抑制异常。** 被抑制的那条与代表它的那条是同一服务同一指标上的同一类问题，
计入就会把一个故障数成两遍。

**2. 服务维度覆盖全部服务**（含外部依赖）。无异常的服务 `max_level` 为空、影响面为 0——
「哪些服务是干净的」本身就是统计要回答的问题，只列异常服务反而要求读者自己去对照服务清单。

**3. 影响面 = 出现异常的实例数 / 实例总数**，分母取配置声明的实例清单，分子只认声明过的实例名。
这一条在实现时踩过一次：链路健康度（BIZ-06）的 `instance` 字段装的是链路上最弱节点的
**服务名**（不是实例名），直接计数会算出 133% 这种不可能的影响面。
这类链路级异常仍计入服务的异常数，只是不占实例影响面——
「链路整体劣化」和「某台机器坏了」本来就不是一件事。

### 集群归属

集群在 `config/services.yaml` 顶层定义，服务通过 `cluster` 字段引用：

```yaml
clusters:
  trade: 交易集群
  payment: 支付集群

services:
  gateway:
    cluster: trade
```

引用了未定义的集群会在**启动期直接报错**。拼错一个字母就会把一个服务静默分到错误的集群，
而报告上看起来毫无异常——这类错误必须在启动时暴露，不能等读者去比对配置。

### 为什么统计不参与评分

统计是只读聚合，不产出「服务分」「集群分」。再引入一套聚合评分，同一批异常就会衍生出
第二套互相矛盾的数字（稳定性评分 vs 服务分），读者要同时记住两套口径；
而题目要求的是「巡检统计」，不是第二套评分模型。
