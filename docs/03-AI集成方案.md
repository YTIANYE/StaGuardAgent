## 一、总体设计

```
                     ┌──────────────────────┐
  16 条规则 + 动态基线 │  原始发现 AnomalyFinding │
                     └──────────┬───────────┘
                                ▼
                     ┌──────────────────────┐
                     │  聚合 / 抑制 / 聚类    │  ← 去重、影响面回填、拓扑传播聚类
                     └──────────┬───────────┘
                                ▼
                     ┌──────────────────────┐
       依赖拓扑 ─────►│   证据包 Evidence      │◄───── 变更事件
       历史同类事件 ─►│   （只有事实，无结论）   │◄───── 数据质量报告
                     └──────────┬───────────┘
                                ▼
                     ┌──────────────────────┐
                     │  大模型（DeepSeek 等） │  强 schema 约束 + response_format=json_object
                     └──────────┬───────────┘
                                ▼
                     ┌──────────────────────┐
                     │  校验与修复            │  枚举纠偏 / 幻觉引用剔除 / 漏答补齐
                     └──────────┬───────────┘
                                ▼
                     ┌──────────────────────┐
                     │  三级降级兜底          │  LLM → 规则决策树 → 纯统计
                     └──────────────────────┘
```

**贯穿全流程的一条约束：AI 挂了报告照样出得来，而且报告里会如实标注降级。**

## 二、证据包（Evidence Bundle）

证据包是 AI 归因质量的决定性变量：**喂结论，模型复述结论；喂事实，模型才可能推理。**

### 四类刻意放进来的证据

| 证据 | 为什么它能提高归因质量 |
| --- | --- |
| **依赖拓扑** | 让模型自己判断传播方向。没有拓扑，「网关和银行渠道都报警」就只能靠猜 |
| **变更记录** | 因果推理里最强的证据：异常起始与变更时间高度重合时，「变更引入」几乎可以直接定性 |
| **时序摘要** | 让模型看见「还在涨」。摘要而非原始点：30 个点对判断趋势的边际价值很低，几十条序列全塞进去会挤爆上下文 |
| **历史同类事件** | 让模型识别复发。带相似度与历史根因，于是它可以说出「这是复发问题，上次的处理方式是 X」 |

### 三类刻意排除在外的内容

| 排除项 | 原因 |
| --- | --- |
| 规则的分级结论 | 会让模型倾向复述而不是推理 |
| 原始时序全量点 | 成本高、边际价值低、模型会淹死在数字里 |
| 与异常服务无关的变更 | 减少干扰项。但**保留「时间接近但因果无关」的变更**——正是它们让「看到变更就说是变更引入」的懒惰推理暴露出来 |

## 三、提示词

### System Prompt（全文）

```
你是一名资深 SRE，正在对线上业务做稳定性巡检的根因分析。你会收到一份**证据包**，
里面只有客观事实：指标偏离、服务依赖拓扑、变更记录、历史同类事件。

请严格遵守以下约束：

1. 只为证据包中实际出现的 cluster_id 输出结论，不要臆造不存在的簇。
2. 每条结论必须引用 evidence_ids，且只能引用证据包里真实存在的 evidence_id。
   没有证据支撑的判断请降低 confidence，并在 uncertainties 中说明。
3. root_cause_category 只能取以下枚举值之一：
   traffic_fluctuation（流量波动）、resource_bottleneck（资源瓶颈）、code_defect（代码异常）、
   dependency_failure（依赖故障）、change_induced（变更引入）、capacity_config（容量/配置问题）、
   unknown（证据不足）。

4. **root_cause_category 描述的是「触发机制」，不是「最先失守的环节」。**
   先回答「是什么把系统推动到了这个状态」，再回答「哪个服务最先扛不住」——
   后者写在 root_cause_service 里。两者常常不是同一个服务，这不是矛盾。

5. 类别的判定口径（请严格对齐，这几组的边界很容易混）：
   - traffic_fluctuation：全链路多个服务的流量出现同向、同幅度变化，
     且没有证据表明某个服务在流量变化之前就已劣化。即使下游服务因此资源打满、
     成功率下跌，只要资源打满是流量的结果，类别仍然是 traffic_fluctuation。
     **该类别描述的是观测到的现象，不要求指出外部触发源**——
     触发源未知就写进 uncertainties，不要因此退回 unknown。
   - resource_bottleneck vs capacity_config：前者是「资源在当前配置下被用到打满」，
     是可观测的水位事实；后者是「配置本身设置得不合理」。
     两者都说得通时优先选 resource_bottleneck。
   - dependency_failure：仅当被依赖的一方也在本次异常中劣化时才使用。
     若异常服务在拓扑中已是最下游，就不要把原因推给「它的下游」——
     那是不可观测的臆断。

6. **变更是否可作为根因**：只有发生在异常起始前 30 分钟内、且作用在异常链路上时，
   才可以归为 change_induced。证据包的 `changes` 字段已给出每条变更
   距异常起始的分钟数与 `within_30min_window`，请直接使用。

7. 区分「根因」和「影响面」：根因是导致其余异常的那个源头，影响面是被它带崩的上游服务。
   propagation_path 描述的是影响传播方向（下游 -> 上游），不要把它当作根因链。
   请用 root_cause_service 明确给出根因所在服务名（必须是拓扑里存在的服务）。

8. overall_score_adjust 只能取 -5 到 5 之间的整数，用于微调规则算出的分数。
   绝大多数情况应当给 0；只有当你认为规则的分级与真实影响明显不符时才调整。
9. suggestions 要具体可执行（谁、做什么、怎么做），不要写「建议排查」「加强监控」这类空话。
10. uncertainties 里如实列出你无法从证据中确认的部分。承认不确定比编造一个自信的答案
    有价值得多，但**不要用 uncertain 来回避结论**。
11. 只输出 JSON，不要任何解释性文字或 Markdown 代码块。
```

**几条约束背后的意图**：

- 第 4、5 条都是**实测改出来的**，不是一开始就想到的。第 4 条针对「把最先失守的环节
  当成触发机制」——模型看到订单服务 CPU 打满就把类别写成资源瓶颈，
  而 CPU 打满其实是流量上涨的结果；第 5 条针对另一个方向的误判——
  模型因为「不知道外部流量为什么掉了」而退回 `unknown`，
  把「描述现象」的类别误解成「需要指出触发源」；
- 第 6 条的字段化处理体现了一条通用原则：**别让模型做它不擅长的机械计算**。
  早期只给变更的绝对时间戳，模型引用了一条 42 分钟前的变更当成因；
  把「距异常起始多少分钟」预计算好放进字段后，同类错误再没出现；
- 第 7 条针对一个很常见的误读：模型容易把 `propagation_path`（展示用的影响传播方向）
  当成根因链，于是得出「根因在网关」；
- 第 8 条把 AI 的评分权限硬性限制在 ±5，守住「分数由规则决定」这条边界；
- 第 10 条要求模型自陈局限。**承认不确定比编一个自信的答案有价值得多**，
  而且它会被写进报告，让读者知道结论的成色。

> 完整的实测调优过程（含每一版提示词为什么改）见
> [`samples/AI对比说明.md`](samples/AI对比说明.md)。

### 输出 schema

```python
class AIAnalysis(BaseModel):
    overall_score_adjust: int                 # 硬边界 ±5，超出由 validator 裁剪
    summary: str                              # 风险总结，2~4 句
    findings: list[Finding]                   # 所有异常项的根因推理
    trend: TrendJudgement                     # direction / reasoning / forecast
    stability_advice: list[str]               # 长期治理方案
    uncertainties: list[str]                  # 证据不足之处

class Finding(BaseModel):
    cluster_id: str
    root_cause_category: RootCauseCategory    # 强枚举
    root_cause: str
    root_cause_service: str | None            # AI 认定的根因服务（用于与规则判断交叉校验）
    confidence: float                         # 0~1
    evidence_ids: list[str]                   # 必须引用真实证据
    impact: str
    suggestions: list[str]                    # 可落地建议
    is_recurring: bool
    owner_hint: str | None
```

`root_cause_service` 是刻意从自然语言里单独拉出来的字段：
有了它，「AI 的判断与规则聚类的判断是否一致」才能变成一个**可机械校验**的事实。
只比较自然语言里有没有某个词是不可靠的——那种检查要么永远触发、要么永远不触发，等于没有。
两者不一致时报告会显式标注 `⚠️ 根因定位分歧` 并同时给出双方依据。

传输层用 `response_format={"type": "json_object"}`，pydantic 做本地强校验。

## 四、校验与修复

模型输出**不做「全有或全无」的校验**：写错一个枚举值不该导致整份分析被丢弃。

| 情况 | 处理 |
| --- | --- |
| `cluster_id` 不在证据包里 | 丢弃该条结论并记录 |
| `root_cause_category` 非枚举值 | 归为 `unknown` 并记录 |
| `evidence_id` 不存在 | 剔除该引用并记录；若剔除后无有效引用，置信度封顶 0.4 |
| `overall_score_adjust` 越界 | 裁剪到 ±5 |
| 顶层结构非法（findings 不是列表） | 判为失败，触发重试 |
| 某个簇没有被回答 | 用规则归因补齐并记录 |

**为什么要清掉编造的引用**：模型很擅长给出「看起来很专业」的引用。
如果不校验，报告里就会出现指向不存在证据的结论；读者一核对发现对不上，
整份报告的可信度就没了。

**为什么要补齐漏答的簇**：模型只回答了一部分簇是常见情况（尤其是簇很多时）。
漏掉的簇不能从报告里消失——覆盖完整性优先于来源纯净。

所有修复动作都会追加到 `uncertainties`，读者能看到哪些结论是「修过的」。

## 五、三级降级

| 级别 | 触发条件 | 产出 | 标注 |
| --- | --- | --- | --- |
| 1. 大模型 | 正常路径 | 上下文推理 + 自然语言表达 | `degraded=false` |
| 2. 规则决策树 | 未配凭据 / 调用失败 / 重试耗尽 / 返回非法 | 按证据特征判定的归因结论 + 处置建议 | `degraded=true` + 具体原因 |
| 3. 纯统计 | 连规则归因都算不出来（理论上不会发生） | 只报事实 | `degraded=true` |

### 重试策略

- **凭据缺失属于确定性失败，直接降级不重试**——重试只是浪费时间和配额；
- 网络/限流类错误重试 `llm_max_attempts` 次，指数退避（1.5s × attempt）；
- 每次调用都记录 token 用量与耗时，写进 `AIMeta` 落库，报告附录里展示。

### 规则决策树（降级路径的核心）

**判别顺序的关键是先看「主根因这条异常本身是什么」，再看簇里还有哪些信号。**

```
1. 异常起始与变更时间高度重合（≤30 分钟）    → change_induced
2. 主根因本身就是流量异常                    → traffic_fluctuation（若有资源压力则附加容量建议）
3. 主根因是连接池打满 + 延时恶化
     ├─ 本服务有受影响的下游                   → dependency_failure
     └─ 本服务在链路最下游（无下游可指）        → resource_bottleneck
4. 主根因是 CPU / 内存 / 连接水位越线          → resource_bottleneck
5. 主根因是内存单调增长                      → code_defect（走代码修复而非扩容）
6. 主根因是实例间严重倾斜                    → capacity_config
7. 主根因是业务错误率飙升                    → code_defect
8. 主根因是纯性能劣化                        → resource_bottleneck
9. 只有成功率 / 链路健康度异常                → unknown（缺少定位性证据）
```

顺序反了会经常误判。例如先看「簇里有没有 RES-04」：
一次资源瓶颈造成的雪崩里，连接池打满往往只是被影响的一方，
而真正打满 CPU 的那个服务才是根因。

第 3 步为什么要分叉：早期实现直接判为 `dependency_failure`，
说「连接池被慢请求占满，指向其**下游依赖**响应退化」。
但在 S1 场景里，`bank-channel` 在拓扑中是**叶子节点**（外部依赖，没有更下游），
这句话陈述的是一个**不可观测的事实**——审阅者一核对拓扑就会发现站不住脚。
**宁可给出保守但站得住的结论，也不要给出专业但无依据的结论。**

实测：在完全不接入大模型的条件下，这棵决策树在 7 个场景上达到
**根因命中率 100%、级别命中率 100%、误报率 0%**。
这意味着即使 AI 全程不可用，巡检系统也不会退化成不可用；
接入真实模型后，这个成绩没有变化——**模型的收益不在准确率上**，
而在结论的可执行性上（见 [`samples/AI对比说明.md`](samples/AI对比说明.md)）。

## 六、复发识别（不用向量库）

### 做法

根因簇的签名是它包含的 `服务.指标` token 集合：

```
"bank-channel.conn_usage&bank-channel.success_rate&gateway.success_rate&..."
```

两次同类故障只要涉及相同的服务和指标，签名就高度重合。
相似度用 Jaccard，阈值 0.6。

### 为什么不用向量库

巡检历史检索有个很好的性质：异常簇已经被归一成结构化签名，
同类故障的签名天然高度重合。

用签名的额外收益是**完全可解释**——报告里能写出：

> 与 3 天前的 `run-20260922-100000-S1` 相似度 0.86，当时根因是依赖故障

向量相似度说不出这句话。代价是零额外依赖、零额外存储组件。
对一个单机可跑的巡检系统，这是明显更划算的取舍。

## 七、归因质量评测

### 方法

把 7 个场景变成 7 道可判定的题目（`staguard/evaluation.py`），用真实模型跑一遍，量化三个指标：

| 指标 | 定义 |
| --- | --- |
| **根因命中率** | AI 给出的根因类别是否落在期望集合内 |
| **级别命中率** | 最严重异常的定级是否与期望一致 |
| **误报率** | 正常态场景是否被误判成故障 |

```bash
make eval    # 或 staguard eval
```

### 两个判定口径说明

1. **根因允许多个正确答案**。内存泄漏既可归为「资源瓶颈」也可归为「代码异常」，
   两者都能推出正确的处置动作，不应判错（配置项 `also_accept`）；
2. **正常态的「干净」标准是无 P1/P2，而不是零异常**。要求零异常等于要求规则对噪声
   零敏感，那在真实系统里不可能做到。巡检的目标是把误报压到「不打扰人」的量级。

### 场景与被验证的能力

| 场景 | 注入 | 期望根因 | 被验证的能力 |
| --- | --- | --- | --- |
| S0 | 无（仅噪声与毛刺） | none | **不误报**——比报出异常更难 |
| S1 | 银行渠道 P99→3.2s，支付连接池打满 | dependency_failure | 拓扑传播 + 根因簇 + 区分根因/影响面 |
| S2 | 库存服务单实例 CPU 96% | resource_bottleneck | **单实例异常识别**（而非笼统的服务级告警） |
| S3 | 订单/网关 QPS ×3，成功率正常 | traffic_fluctuation | 区分「异常」与「故障」，并给出容量风险 |
| S4 | 用户服务发布后业务错误率 0.1%→5.4% | change_induced | **技术成功率的盲区** + 变更关联（含无关变更干扰项） |
| S5 | 网关 QPS −72%，全链路静默 | traffic_fluctuation | 静默故障——监控全绿，业务已经没单了 |
| S6 | 支付内存 24 小时线性增长 | resource_bottleneck / code_defect | 慢故障 + 趋势外推 OOM 时间 |

`config/changes.yaml` 里的 `defaults` 区刻意放了三条**背景变更**（与本次异常时间无关），
它们对 S1/S4 可见。没有干扰项的归因题目等于送分题，
只有存在「时间上接近但因果无关」的变更，才能检验模型是否真的在做因果推理。
