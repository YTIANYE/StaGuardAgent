# 演示脚本与讲解口径

> 面向：现场/视频演示、面试讲解
> 总时长：约 12 分钟（含追问余量）
> 一句话定位：**「它不只是把告警列出来，而是告诉你根因在哪、先做什么。」**

---

## 〇、开场三十秒

> 「传统巡检靠人定时核对成功率、延时、报错、资源水位，问题是**滞后、漏检、而且报出来的是一堆症状不是原因**。
> 这套系统把链路自动化了，重点解决两件人工做不到的事：
> **一是用动态基线代替固定阈值**，二是**把一堆孤立异常收敛成一个根因加一片影响面**。
> 下面我用五个场景走一遍。」

先一句话交代技术栈（不展开）：
Python + FastAPI + SQLAlchemy Core + SQLite，**未配置大模型时自动降级为规则归因**，今天演示的就是降级路径——这本身就是设计的一部分。

---

## 一、环境准备（演示前 3 分钟做好）

```bash
cd StaGuardAgent
make install          # 首次约 60s
make gen-data         # 生成 14 天归档 + 7 个故障场景，约 15s
```

演示过程中如果被人要求现场重来，`make clean && make gen-data` 即可，**数据是固定随机种子生成的，结果完全可复现**。

可选：另开一个终端跑 `make monitor`，这样能演示 HTTP 数据通道。

## 二、演示动线（5 个场景，每个 1.5~2 分钟）

### 第 1 幕：先证明「它不乱报」——正常态 S0

```bash
make run SCENARIO=S0
```

**要指着屏幕说的**：

- 评分 96.4，**没有 P1/P2**，只有 1 条 P4（内存轻微偏离基线）。
- 「这一条我不打算修——**零异常不是目标，不打扰人才是**。规则对噪声零敏感在真实系统里做不到，
  能做到的是把误报压到不打扰人的量级。误报比漏报更致命，因为告警疲劳会让真正的 P1 一起被忽略。」

> **为什么把这幕放第一个**：面试官最想确认的就是「这系统会不会天天瞎报」。
> 先给一个干净的结果，后面所有报警的可信度都建立在这上面。

---

### 第 2 幕：主戏——依赖故障引发的雪崩

```bash
make run SCENARIO=S1
```

**要指着屏幕说的（按顺序）**：

1. **评分 20.4 / E 严重，24 条 P1**，看起来是全面崩溃；
2. **扣分明细**里可用性被扣满 40 分——因为「错误预算消耗达允许值的 287 倍」，
   这是 SRE 的标准口径，不是「成功率低于 X 就扣 Y 分」的拍脑袋映射；
3. 翻到「**根因分析**」章节：
   - 传播路径 `gateway → order-svc → payment-svc → bank-channel`；
   - **根因是 `bank-channel`（银行渠道），不是网关**。
   > 「网关的 P1 看起来最刺眼——入口成功率跌了 6 个点。但它是**被传导上来的影响面**。
   > 真正的原因在链路最下游：银行渠道的连接池被打满、P99 从 200ms 涨到 3.5 秒，
   > 导致支付服务连接堆积，再一层层把订单和网关拖垮。」
4. 翻到「**修复建议**」：分「立即止血 / 短期加固 / 长期治理」三档，带责任方（支付组）。

> **这幕的核心卖点**：24 条异常 → **1 个根因 + 3 个影响面**。
> 「如果不做这一步聚类，AI 拿到的就是 24 条互不相干的异常，
> 它只能给出 24 个互相独立的猜测——因为**输入本身没告诉它这些异常之间有关系**。」

---

### 第 3 幕：反直觉的那一幕——流量突增不是故障

```bash
make run SCENARIO=S3
```

**要指着屏幕说的**：

- QPS 涨到基线 3 倍，但**成功率、错误率全程正常**；
- 根因判定是「**流量波动**」而不是「订单服务故障」；
- 但评分仍然只有 45 分，因为**订单服务 CPU 被推到 99% 连续 21 分钟**；
- 修复建议里既说了「核对容量水位，确认是否为预期活动流量」，
  也单独拎出了「按当前峰值反推所需容量并预留 30% 余量」。

> 「这是我最想展示的一个判断：**流量上涨本身不是故障，但它可能是事故的驱动因素**。
> 一个只会看阈值的系统会在这两种结论之间二选一，要么误判成 P1 事故，
> 要么因为业务指标正常就说『一切正常』。正确的答案是**两句话都说**。」

---

### 第 4 幕：技术监控看不见的那类故障——变更引入

```bash
make run SCENARIO=S4
```

**要指着屏幕说的**：

- 用户服务发布 v1.9.0 之后，**业务错误率从 0.1% 飙到 5.4%**；
- 但**技术成功率基本是正常的**——因为 HTTP 还是 200，失败发生在业务层；
- 归因结论是「变更引入」，依据是「异常起始 09:48 与 09:45 的发布高度重合」。

> 「这是技术监控的典型盲区：接口可用性看着 100%，用户其实已经登不上去了。
> 我们专门有一条 `BIZ-02 业务错误率` 规则盯着这个缝。
> 另外注意，变更记录里**还有两条与本次无关的背景变更**——
> 一个只会说『看到变更就怀疑变更』的系统在这里就会归错因。」

---

### 第 5 幕：慢故障与趋势外推

```bash
make run SCENARIO=S6
```

**要指着屏幕说的**：

- 内存 24 小时线性增长，**每一分钟的瞬时水位都在阈值内**；
- 输出是「内存持续增长（每小时 3.4%），**按当前斜率外推，约 0.3 小时后触及 95% 危险水位**」；
- 定级 P1，因为**它马上就要 OOM 了**。

> 「这类故障任何固定阈值都抓不到——它每分钟都是正常的。
> 只有趋势型规则能提前发现，而趋势规则能做的前提是**采集窗口够长**。
> 所以我们的采集范围不是拍脑袋定的 30 分钟，而是**由规则的观察窗反推出来的 24 小时**。」

## 三、收尾：三个工程细节（各 30 秒）

### 1. AI 挂了报告照样出得来（两版报告现场对比）

```bash
diff docs/samples/S1-rule-fallback.md docs/samples/S1-llm.md
```

> 「左边这份是把 API key 抽掉跑出来的——系统**自动降级**为规则决策树归因，
> 报告照样完整，而且在附录里**如实标注 `degraded=true` 和降级原因**。
> 金融场景里『因为 AI 挂了所以今天不出巡检报告』是不可接受的。
>
> 右边这份是接真实大模型的版本。注意看：**评分、定级、根因结论两边完全一样**，
> 差别只在结论的**可执行性**——」
>
> - 兜底版：`先摘除 bank-channel-0 观察整体水位是否回落，再评估扩容`
> - 模型版：`立即对 bank-channel 连接池做紧急扩容（提高 max connections 或增加实例），
>   并临时下调 payment-svc 对 bank-channel 的并发调用量以释放连接占用`

> 「所以我们的分工是：**规则负责『站得住』**（评分、定级、根因定位，这些要可复现
> 可对账），**模型负责『用得上』**（把结论翻译成能直接动手的东西）。」

**顺手给出量化**：

```bash
make eval
```

> 「七道题，**两条路径都是根因命中率 100%、级别命中率 100%、误报率 0%**。
> 也就是说 AI 不可用时系统不会退化成不可用，接入模型后准确率也不会更高——
> 收益全在建议的可执行性上。这个结论本身我相信比『接了模型更准』更值得说。」

**如果被追问「那接入模型图什么」**：

> 「图三件事：一是建议能带参数和验收标准；二是影响面描述具体 2~5 倍；
> 三是**它是一个独立的第二意见**。开发过程中我们规则兜底有个缺陷——
> 对着没有下游的银行渠道说『它的下游依赖退化』——正是靠模型给出不同结论才发现的。
> 报告里遇到分歧会显式标注，**两条独立路径的分歧点就是缺陷藏身的地方**。」

### 2. 两条数据通道结果完全一致

```bash
make monitor &          # 另开终端
make run SCENARIO=S5 SOURCE=http
make run SCENARIO=S5 SOURCE=file
```

> 「文件通道和 HTTP 通道读的是同一份底层数据，所以结论必然一致。
> 一致性是被构造出来的，不是靠嘴保证的。
> 接 Prometheus 只需要多加一个 `MetricSource` 实现，编排逻辑一行不动。」

### 3. 服务化与 K8s

```bash
make serve &
curl -s localhost:8080/readyz | python -m json.tool
curl -s localhost:8080/metrics | head -6
```

> 「`/readyz` 不是 `return 200`——它真的去查数据库连通性和数据集是否已初始化。
> 一个『进程活着但数据库连不上』的实例，不摘流量就会持续返回 500。
> 另外 liveness 用 `/healthz`、readiness 用 `/readyz`：依赖挂了应该摘流量，
> 不应该重启进程，否则会引发惊群。」

## 四、高频追问与回答要点

| 追问 | 回答要点 |
| --- | --- |
| **为什么不用固定阈值？** | 固定阈值在凌晨必然误报、在晚高峰必然漏报，因为业务流量本身有周期。我们按「同星期几 + 同小时」取样，两层周期同时消掉。 |
| **基线的历史里混着故障怎么办？** | 用中位数 + MAD 而不是均值 + 标准差。实测 190 个正常点混 10 个故障点（3000ms）时，中位数口径的基线还在 102 附近，均值已经被拉到 240 以上。**一个会被一次故障永久抬高的基线，比固定阈值更危险**，因为它会让人以为「已经动态适配了」。 |
| **为什么让 AI 打分只给 ±5？** | 三件事：可复现（同一份数据必须同一个分数，否则多次对比没意义）、可解释（报告要能回答「这 12 分扣在哪」）、抗幻觉。让模型做它擅长的（归因、表达），不做需要一致性的（打分）。 |
| **怎么防止 AI 胡说？** | 四道闸：①证据包只放事实不放规则结论，让它无法复述；②`response_format=json_object` + pydantic 强校验；③**校验它引用的 evidence_id 是否真实存在，编造的剔除并降低置信度**；④要求它输出 `uncertainties` 自陈证据不足。 |
| **AI 和规则结论不一致怎么办？** | 报告里会显式标注 `⚠️ 根因定位分歧`，把双方的依据并列展示。**这种分歧恰恰是最值得人工看一眼的地方，把它藏起来等于丢掉一次发现问题的机会。** |
| **聚类凭什么说银行渠道是根因？** | 四个信号加权：信号性质（资源/性能类更像「因」，业务类更像「果」）、严重度、传播方向（瓶颈类越靠下游越像根因，症状类越靠上游越像根因）、时序（最先出现症状的）。另加两条硬规则：链路健康度这类聚合指标永远不能当根因；全链路流量同向变化时根因只在入口。 |
| **为什么不用向量库做历史相似检索？** | 异常簇已经被归一成 `服务.指标` 的 token 签名，两次同类故障天生高度重合。用 Jaccard 的额外收益是**完全可解释**——报告能写出「与 3 天前 run-xxx 相似度 0.86，当时根因是依赖故障」。向量相似度说不出这句话，而且多引入一个存储组件。 |
| **数据量大了怎么办？** | 存储层用 SQLAlchemy Core 写，换 `STAGUARD_DB_URL` 到 PostgreSQL 即可，业务代码零改动。目前在 200 万点 / 368MB 的单机 SQLite 上，单次巡检 1~5 秒。 |
| **为什么巡检是 15 分钟一次而不是 1 分钟？** | 巡检窗口是 30 分钟，1 分钟一次会让相邻两次的结论有 94% 的数据重叠，产生大量无意义的报告和告警。**巡检频率应当与「业务能容忍的最长故障发现时间」对齐，不是越快越好。** |

## 五、一句话收尾

> 「这套系统的核心判断是：**巡检的价值不在于把异常都找出来，而在于把异常变成一个能直接执行的动作。**
> 所以我在三件事上花了最多力气——动态基线让告警可信、根因聚类让结论可执行、
> 三级降级让系统在任何情况下都给得出结论。」
