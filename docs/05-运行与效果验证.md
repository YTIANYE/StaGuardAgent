# 运行与效果验证

> 配套命令：`Makefile`　|　场景定义：`config/scenarios.yaml`
> 本文给出从零跑通全流程的步骤、每一步的预期输出，以及各场景分别验证了哪项能力。

---

## 一、环境准备与数据生成

```bash
cd StaGuardAgent
make install          # 首次约 60s
make gen-data         # 生成 14 天归档 + 7 个故障场景，约 15s
```

数据集由固定随机种子生成，`make clean && make gen-data` 可完全复现同一份数据，
因此下文列出的数字都可以在本地复算。

需要验证 HTTP 数据通道时，另开一个终端常驻运行模拟监控接口：

```bash
make monitor
```

## 二、场景运行与预期结果

七个场景的注入内容与期望结论见 [`03-AI集成方案.md`](03-AI集成方案.md) 第七节。
下面列出五个有代表性的场景：运行命令、预期输出，以及这些输出对应的设计依据。

### 1. 正常态 S0 —— 不误报

```bash
make run SCENARIO=S0
```

预期输出：

- 评分 **96.4 / 100（A 优秀）**，**无 P1/P2**；
- 仅 1 条 P4：`order-svc` 内存使用率 61.56%，相对基线 59.37% 的轻微偏离。

设计依据：**零异常不是目标，不打扰人才是。** 规则对噪声零敏感在真实系统里做不到，
能做到的是把误报压到不打扰人的量级——误报比漏报更致命，因为告警疲劳会让真正的 P1
一起被忽略。该口径同时是归因评测中「误报率」的判定标准：正常态场景出现 P1/P2 才算误报，
出现 P4 不算。

### 2. S1 依赖故障雪崩 —— 根因聚类

```bash
make run SCENARIO=S1
```

预期输出（报告按顺序读）：

1. 评分 **20.4 / 100（E 严重）**，异常分布 P1 24 / P2 15 / P3 5 / P4 6；
2. 扣分明细中可用性被扣满 40 分，依据是「gateway 错误预算消耗达允许值的 287.4 倍」——
   这是 SRE 的标准口径（错误预算），不是「成功率低于 X 就扣 Y 分」的映射；
3. 「根因分析」章节只有 1 个簇：
   - 传播路径 `gateway → order-svc → payment-svc → bank-channel`；
   - 主根因是 `bank-channel`（连接池打满），**不是网关**——
     网关的 P1 最刺眼（入口成功率跌了若干百分点），但它是被传导上来的影响面；
4. 「修复建议」分「立即止血 / 短期加固 / 长期治理」三档，并带责任方。

设计依据：24 条 P1 若不做聚类，AI 拿到的是 24 条互不相干的异常，只能给出 24 个互相独立的
猜测——**输入本身没告诉它这些异常之间有关系**。聚类把它收敛成「1 个根因 + 若干影响面」，
这是 AI 归因质量的前提。

### 3. S3 流量突增 —— 异常不等于故障

```bash
make run SCENARIO=S3
```

预期输出：

- QPS 涨到基线 3.24 倍（2449.2 vs 756.4），但**成功率与错误率全程正常**；
- 根因类别判定为「**流量波动**」而不是「订单服务故障」；
- 评分仍只有 **45.0 / 100**，因为 `order-svc` CPU 被推到 99% 并持续 21 分钟；
- 修复建议同时给出两句话：核对容量水位是否为预期活动流量；
  按当前峰值反推所需容量并预留 30% 余量。

设计依据：**流量上涨本身不是故障，但它可能是事故的驱动因素。** 只会看阈值的系统会在这两种
结论之间二选一——要么误判成 P1 事故，要么因为业务指标正常而判定「一切正常」。
正确的答案是两句话都说。

### 4. S4 变更引入 —— 技术监控的盲区

```bash
make run SCENARIO=S4
```

预期输出：

- `user-svc` 发布 v1.9.0 之后，**业务错误率从 0.07% 升到 5.40%**（+5.33 个百分点）；
- **技术成功率基本正常**——HTTP 仍返回 200，失败发生在业务层；
- 归因结论为「变更引入」，依据是异常起始 09:48 与 09:45 的发布高度重合；
- 变更记录里另有两条与本次无关的背景变更，用于检验归因是否会「看到变更就怀疑变更」。

设计依据：接口可用性看着 100%，用户其实已经下不了单。这是技术监控的典型盲区，
因此专门有一条 `BIZ-02 业务错误率` 规则盯着这个缝。

### 5. S6 慢故障与趋势外推

```bash
make run SCENARIO=S6
```

预期输出：

- 内存 24 小时线性增长，**每一分钟的瞬时水位都在阈值内**；
- 结论为「内存持续增长（每小时 3.4%），按当前斜率外推，约 0.3 小时后触及 95% 危险水位」；
- 定级 P1。

设计依据：这类故障任何固定阈值都抓不到——它每分钟都是正常的，只有趋势型规则能提前发现。
而趋势规则成立的前提是**采集窗口够长**，所以采集范围不是固定 30 分钟，而是由规则的
观察窗反推出 24 小时。

## 三、工程特性验证

### 1. 降级路径与非降级路径对比

```bash
diff docs/samples/S1-rule-fallback.md docs/samples/S1-llm.md
```

- `-rule-fallback` 版本是未配置凭据（或调用失败）时产出的：系统自动降级为规则决策树归因，
  报告结构完整，并在附录中标注 `degraded=true` 与降级原因；
- `-llm` 版本是接入真实大模型产出的：**评分、定级、根因结论两边一致**，
  差别在结论的可执行性上。

```bash
make eval
```

七个场景的归因评测在两个模式下均为：根因命中率 100%、级别命中率 100%、误报率 0%。
即系统在 AI 不可用时不会退化成不可用，接入模型后准确率也不会更高——收益体现在建议的
可执行性上（详见 [`samples/AI对比说明.md`](samples/AI对比说明.md)）。

### 2. 两条数据通道的一致性

```bash
make monitor &                              # 另开终端
make run SCENARIO=S5 SOURCE=http
make run SCENARIO=S5 SOURCE=file
```

两个通道读取的是同一份底层数据，因此结论必然一致；`tests/test_e2e.py` 中对评分与
级别分布做了等值断言，一致性是被测试锁住的，不是靠说明保证的。
接入 Prometheus 只需要新增一个 `MetricSource` 实现，编排逻辑无需改动。

### 3. 服务化与探针

```bash
make serve &
curl -s localhost:8080/readyz  | python -m json.tool
curl -s localhost:8080/metrics | head -6
```

`/readyz` 会真实检查数据库连通性与数据集是否已初始化，而不是固定返回 200：
一个「进程活着但数据库连不上」的实例，不摘流量就会持续返回 500。
liveness 用 `/healthz`、readiness 用 `/readyz`——依赖挂了应当摘流量而不是重启进程，
否则会引发惊群。

## 四、设计要点速查

| 问题 | 设计依据 |
| --- | --- |
| 为什么不用固定阈值？ | 固定阈值在凌晨必然误报、在晚高峰必然漏报，因为业务流量本身有周期。按「同星期几 + 同小时」取样，两层周期同时消掉。 |
| 基线的历史里混着故障怎么办？ | 用中位数 + MAD 而不是均值 + 标准差。实测 190 个正常点（100~104）混入 10 个故障点（3000）时，中位数口径的基线仍在 102 附近，均值已被拉到 240 以上。**一个会被一次故障永久抬高的基线，比固定阈值更危险**，因为它会让人以为「已经动态适配了」。 |
| 为什么让 AI 打分只给 ±5？ | 三件事：可复现（同一份数据必须同一个分数，否则多次对比没有意义）、可解释（报告要能回答「这 12 分扣在哪」）、抗幻觉。让模型做它擅长的（归因、表达），不做需要一致性的（打分）。 |
| 怎么防止 AI 胡说？ | 四道闸：①证据包只放事实不放规则结论，让它无法复述；②`response_format=json_object` + pydantic 强校验；③校验它引用的 `evidence_id` 是否真实存在，编造的剔除并降低置信度；④要求它输出 `uncertainties` 自陈证据不足。 |
| AI 和规则结论不一致怎么办？ | 报告里会显式标注 `⚠️ 根因定位分歧`，把双方的依据并列展示。这种分歧恰恰是最值得人工看一眼的地方，把它藏起来等于丢掉一次发现问题的机会。 |
| 聚类凭什么判定银行渠道是根因？ | 四个信号加权：信号性质（资源/性能类更像「因」，业务类更像「果」）、严重度、传播方向（瓶颈类越靠下游越像根因，症状类越靠上游越像根因）、时序（最先出现症状的）。另加硬规则：链路健康度这类聚合指标永远不能当根因；全链路流量同向变化时根因只在入口。 |
| 为什么不用向量库做历史相似检索？ | 异常簇已经被归一成 `服务.指标` 的 token 签名，两次同类故障天生高度重合。用 Jaccard 的额外收益是**完全可解释**——报告能写出「与 3 天前 run-xxx 相似度 0.86，当时根因是依赖故障」。向量相似度说不出这句话，而且要多引入一个存储组件。 |
| 数据量大了怎么办？ | 存储层用 SQLAlchemy Core 写，换 `STAGUARD_DB_URL` 到 PostgreSQL 即可，业务代码零改动。目前在 200 万点 / 368MB 的单机 SQLite 上，单次巡检约 5 秒（规则归因路径，大头是读 14 天归档算基线），接入大模型后约 13 秒。 |
| 巡检为什么是 15 分钟一次而不是 1 分钟？ | 巡检窗口是 30 分钟，1 分钟一次会让相邻两次的结论有很大比例的数据重叠，产生大量无意义的报告和告警。巡检频率应当与「业务能容忍的最长故障发现时间」对齐，不是越快越好。 |

## 五、小结

巡检的价值不在于把异常都找出来，而在于把异常变成一个能直接执行的动作。
为此投入最多的三件事是：**动态基线让告警可信、根因聚类让结论可执行、
降级链让系统在任何情况下都给得出结论。**
