## 二、三步跑通

```bash
make install                        # 建 venv 并装依赖
make gen-data                       # 生成 14 天归档 + 7 个故障场景（固定种子，可复现，约 15s）
make run SCENARIO=S1                # 跑一次巡检，报告写进 reports/S1/
```

Windows 用户：在项目根目录执行 `run.bat` 即可，等价于上面三步（不需要 `make`、不需要激活虚拟环境）。

不配任何凭据也能跑：AI 会自动降级为规则决策树归因，并在报告附录如实标注 `degraded=true`。
想接真实大模型，把 key 填进 `.env` 即可（参考 `.env.example`）。

其它常用入口：

```bash
make demo            # 一键：生成数据 + 跑测试 + 巡检 S0/S1 + 归因评测
make eval            # 归因评测：根因命中率 / 级别命中率 / 误报率
make monitor         # 启动模拟监控接口（HTTP 采集通道的对端，另开终端）
make run SCENARIO=S5 SOURCE=http   # 用 HTTP 通道巡检，验证数据源可插拔
make serve           # HTTP 服务：/healthz /readyz /metrics、手动触发巡检
make schedule        # 常驻定时巡检（K8s 里也可换成 CronJob）
```

> Windows 上的脚本用法、配 key 与环境差异见 [`07-运行指南.md`](07-运行指南.md)。

## 三、题目要求逐条验收对照

### 3.1 整体要求

| 题目要求 | 验收动作 |
| --- | --- |
| 支持模拟/对接业务监控数据源 | `make run SCENARIO=S5 SOURCE=file` 与 `SOURCE=http` 两次结论一致；实现见 `staguard/collector/` |
| 全自动定时巡检、异常识别、风险分级 | `make schedule`（APScheduler）或 `deploy/k8s/30-cronjob.yaml`；四级分级见 `config/rules.yaml` 的 `levels` |
| 引入 AI 完成根因分析、稳定性评分、优化建议 | `make run SCENARIO=S1` 看报告第二 / 五 / 六章；方案见 [`03-AI集成方案.md`](03-AI集成方案.md) |
| 代码工程化、模块化、可配置、日志、异常处理、配置管理 | 模块表见 [`01-设计文档.md`](01-设计文档.md) §三；日志 `logs/staguard.log`（JSON，10MB × 5 轮转）；阶段隔离见 `staguard/orchestrator.py` |
| 容器化 + K8s 常驻部署（方案设计即可） | `Dockerfile`（非 root UID 10001 + HEALTHCHECK）、`deploy/k8s/`（Deployment + CronJob + HPA） |

### 3.2 核心功能（必做）

| 题目要求 | 实现 | 验收动作 |
| --- | --- | --- |
| 数据源接入（本地文件 / 模拟 HTTP 二选一） | **两条都实现**，共用同一份底层数据 | `make monitor` 后跑 `SOURCE=http`，或看 `tests/test_e2e.py::test_both_sources_produce_identical_verdicts` |
| 数据标准化解析、清洗、结构化存储 | 单位统一 / 越界剔除 / 时间对齐 / 缺失处理 | [`04-数据结构.md`](04-数据结构.md)；`staguard/normalize/cleaner.py` |
| 规则引擎：业务层 | BIZ-01 成功率下跌、BIZ-02 业务错误率、BIZ-03 突增、BIZ-04 突降、BIZ-05 报错量飙升、BIZ-06 链路异常 | [`02-规则设计.md`](02-规则设计.md) 规则清单 |
| 规则引擎：性能层 | PERF-01 P99 超时、PERF-02 P95 超时、PERF-03 响应抖动（另有 PERF-04 长尾、PERF-05 劣化趋势） | 同上 |
| 规则引擎：资源层 | RES-01 CPU、RES-02 内存、RES-04 连接数打满（另有 RES-03 内存增长趋势、RES-05 实例不均衡） | 同上 |
| 自动匹配阈值、识别异常实例、标记异常级别 | 阈值按服务 SLO 自动缩放；异常落到 `服务/实例/指标` 粒度；四级为 紧急/严重/一般/轻微（P1~P4） | `config/thresholds.yaml`、`config/services.yaml`；报告第三章异常清单 |
| AI 输出：稳定性评分（0-100） | 规则可解释算分 + AI ±5 微调（`config/scoring.yaml`，理由见 ADR-1） | 报告第一章「扣分明细」 |
| AI 输出：根因推理 / 修复建议 / 风险总结与趋势 | 与题目四项一一对应 | 报告第二、五、六、七章 |
| 报告：控制台结构化输出 | 评分卡 + 等级分布 + 异常 Top + 根因簇 + 趋势 | 直接看 `make run` 的终端输出 |
| 报告：导出 Markdown | 固定八章 | `reports/<场景>/<run_id>.md` |
| 报告：记录巡检日志 | structlog + `staguard runs` 历史列表 | `logs/staguard.log` |
| 报告：多次巡检结果对比 | 新增异常 / 已恢复 / 持续未解决 / 历史复发 四类 | 连跑两次 `make run SCENARIO=S1`，看报告第七章 |

### 3.3 可选加分项（4/4 均已实现）

| 加分项 | 验收动作 |
| --- | --- |
| 动态阈值替代固定阈值 | 报告附录「动态基线覆盖」；把 `STAGUARD_BASELINE_MIN_SAMPLES` 调到远超样本量（如 999999）即可复现「全部回退静态阈值」，报告会标注覆盖率 0% 与置信度下降 |
| 巡检告警推送（钉钉/企微，模拟即可） | 默认 dry-run，报文落盘 `reports/alerts/`；实现见 `staguard/notify/webhook.py` |
| 服务维度 / 集群维度多粒度统计 | 报告第四章两张表 |
| CLI 交互：单次巡检、定时巡检手动触发 | `make run` / `make schedule` / `curl -X POST localhost:8080/api/v1/inspections` |

## 六、环境与依赖

- Python 3.11+（开发环境为 3.12）；依赖清单见 `pyproject.toml`
