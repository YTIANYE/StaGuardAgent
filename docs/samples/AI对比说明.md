# 规则兜底 vs 真实大模型 · 归因质量对比

本目录同时存放同一批场景的两版报告：

```
S1-rule-fallback.md   未配置 LLM 凭据，自动降级为规则决策树归因
S1-llm.md             调用 DeepSeek（deepseek-chat）完成归因
```

重新生成：

```bash
make sample                                  # 生成 -llm 版本
STAGUARD_LLM_API_KEY= make sample            # 生成 -rule-fallback 版本
```

## 一、量化对比

七个场景的归因评测（`make eval`）结果：

| 指标 | 规则兜底 | 真实大模型 |
| --- | --- | --- |
| 根因命中率 | 100% | 100% |
| 级别命中率 | 100% | 100% |
| 误报率（正常态被判为故障） | 0% | 0% |
| 降级比例 | 100% | 0% |

**两边打平。** 这个结果本身就是第一个结论：**接入大模型不是为了「更准」，规则兜底已经足够准。**
差异在别的地方——下面这张表才是接入模型真正的收益：

| 维度 | 规则兜底 | 真实大模型 |
| --- | --- | --- |
| 影响面描述长度 | 27 ~ 101 字 | 93 ~ 226 字（约 2~5 倍） |
| 置信度 | 固定档位（60% / 65% / 90%） | 随证据强度浮动（55% ~ 82%） |
| 处置建议 | 按类别套模板 | 带上具体的服务、参数与验收标准 |
| 单次耗时 | 0 ms | 5.7 ~ 9.0 s |
| 单次 token | 0 | 3.9k ~ 20.3k |

### 处置建议的差距（原文对照）

**S1 · 依赖故障级联**

> 规则兜底：先摘除 `bank-channel-0` 观察整体水位是否回落，再评估扩容
>
> 大模型：立即对 `bank-channel` 连接池做紧急扩容（提高 max connections 或增加实例），
> 并临时下调 `payment-svc` 对 `bank-channel` 的并发调用量以释放连接占用

**S4 · 变更引入**

> 规则兜底：回滚 `user-svc` 最近一次变更，验证恢复后再做灰度复盘
>
> 大模型：立即回滚 `user-svc` v1.9.0 至上一稳定版本，
> 观察业务错误率是否**在 5 分钟内回落至基线 0.1% 以下**

差别不在「对不对」，而在**能不能直接照着做**：模型给出的建议带了具体的参数
（max connections）、具体的动作（下调并发调用量）、以及可验证的验收标准
（5 分钟内回落到 0.1% 以下）。模板化建议做不到这一点，因为它不知道现场的数字。

> **面试口径**：规则兜底保证「永远有一份站得住的结论」，大模型负责把结论
> 变成「运维看完就能动手」的东西。两者不是替代关系，是**保底与增强**的关系。

## 二、接入真实模型后暴露并修掉的 7 个问题

这一节是本次接入最有价值的部分。**两版报告对比只是一个引子，
真正的收获是它逼出了系统里 6 个此前测不出来的缺陷**——
规则兜底路径永远跑不出这些问题，因为它们全都出在「证据的组织方式」和
「两种归因路径的分歧点」上。

### 1. `max_tokens=2048` 导致输出被截断，而报错信息把人引向错误方向

- **现象**：S1 首次调用返回非法 JSON，重试一次才成功；
- **根因**：一个簇里塞了 50 条异常，模型输出超长被截断。而当时的报错只打印
  内容**开头** 200 字符——截断的 JSON 开头看起来完全正常，
  于是错误信息读起来像「模型格式不稳定」，很容易让人去改提示词；
- **修法**：报错改为打印 `finish_reason` + **结尾** 160 字符，并对
  `finish_reason == "length"` 给出明确提示「调大 STAGUARD_LLM_MAX_TOKENS」；
  `llm_max_tokens` 默认值提到 4096。

> 通用教训：**报错信息要指向正确的原因，否则它比不报错更糟。**

### 2. 提示词没有划清「触发机制」与「最先失守的环节」

- **现象**：S3（流量突增）模型开头就写「入口流量突增至基线 2.6~3.4 倍」，
  却把类别定成了 `resource_bottleneck`；
- **根因**：它把「订单服务 CPU 打满是事实」当成了根因类别，
  而没意识到 CPU 打满是**流量的结果**；
- **修法**：明确写入——`root_cause_category` 描述**触发机制**，
  「哪个服务最先扛不住」写在 `root_cause_service` 里，两者常常不是同一个服务。

### 3. `traffic_fluctuation` 的语义被误解成「必须指出触发源」

- **现象**：S5（入口流量骤降 74%）模型推理完全正确——识别出全链路同向下跌、
  无局部故障特征——但因为「观测不到负载均衡/DNS 侧数据」，
  最终退回了 `unknown`；
- **根因**：它把类别理解成需要回答「为什么流量没了」，
  而该类别的实际语义是「观测到了什么现象」；
- **修法**：明确写入——该类别描述**观测到的现象**，
  外部触发源未知就写进 `uncertainties`，
  **不要因为触发源未知而退回 unknown**；并补一句「不要用 uncertain 来回避结论」。

> 这条改动把 S5 从 `unknown` 修正为 `traffic_fluctuation`（置信度 82%）。

### 4. 证据里没算「变更距异常起始多少分钟」

- **现象**：S1 的归因里引用了一条 **42 分钟前**的配置变更当作成因，
  超出了 30 分钟的相关性窗口；
- **根因**：证据包只给了变更的绝对时间戳，模型需要自己做一次时间差——
  这一步被跳过了；
- **修法**：在证据里**预计算**并显式给出 `minutes_before_earliest_anomaly`
  与 `within_30min_window` 两个字段。

> 通用教训：**别让模型做它不擅长的机械计算**。把差值算好放在字段里，
> 比反复强调「要注意时间」有效得多。

### 5. 规则兜底对着无下游的服务说「它的下游依赖退化」

- **现象**：S1 里规则兜底给出「`bank-channel` 连接池打满，指向其**下游依赖**响应退化」，
  但 `bank-channel` 在拓扑里是**叶子节点**（外部依赖，没有更下游）；
- **发现方式**：正是大模型给出了不同的类别（`resource_bottleneck`）才让人去核对——
  **两种归因路径的分歧点，就是缺陷藏身的地方**；
- **修法**：兜底规则增加判定——只有本服务**有受影响的下游**时才能归为
  `dependency_failure`；否则归为 `resource_bottleneck` 并说明「处于链路最下游，
  无法区分自身能力不足与其外部依赖异常」。同时把两类都加进 S1 的可接受答案。

> 这条最值得讲：**不是 AI 比规则准，而是两条独立路径的分歧暴露了规则里的臆断。**

### 6. 主根因选取被「方向分」带偏，把根因定位到无辜服务

- **现象**：S4（用户服务发布后业务错误率飙到 5.4%）里，规则兜底把根因服务
  判成了 `gateway`——而正确答案是发布变更所在的 `user-svc`；
- **根因**：入口网关因为流量天然波动有一条「成功率略低于 SLO」的 **P4**，
  它在「越靠上游越像根因」这一项上拿满方向分，压过了真正出故障的 **P2**；
- **修法**：主根因**先比严重度，同级之间再比加权分数**——
  一个 P4 级的噪声解释不了下游的 P2 故障；
- **验证**：新增单测 `test_severe_downstream_anomaly_beats_upstream_noise` 锁定该行为。

### 7. 复发识别把「同一窗口重跑」误判成「复发」

- **现象**：评测反复重跑后，报告里开始出现「历史复发」标记；
- **根因**：`recent_clusters` 只按 `run_id` 排除历史，同一故障窗口被重跑时
  签名完全相同，于是被认成复发；
- **为什么必须修**：「同一轮故障被巡检两次」和「修好了又回来了」是两件完全不同的事。
  前者标成复发，读者会以为**修复无效**——这是在制造错误信息；
- **修法**：按 `(scenario_id, window_end)` 排除同一数据窗口的历史。

## 三、结论：两者在系统里的分工

```
                   ┌──────────────────────────────────────┐
   规则引擎 ──────►│  可解释评分（AI 只能 ±5 微调）          │
                   │  主根因选取（严重度优先）              │
                   │  降级归因（决策树，永远可用）           │
                   └──────────────────────────────────────┘
                                   ▲
                                   │ 分歧即信号：
                                   │ 两条路径结论不同 → 值得人工看一眼
                                   ▼
                   ┌──────────────────────────────────────┐
   大模型   ──────►│  自然后语言的风险总结                  │
                   │  带参数与验收标准的处置建议             │
                   │  影响面的具体化描述                    │
                   └──────────────────────────────────────┘
```

- **规则负责「站得住」**：评分、定级、根因服务定位。这些要求可复现、可对账，
  不能交给一个每次可能给不同答案的东西；
- **模型负责「用得上」**：把结论翻译成能直接执行的建议。
- **两者分歧是资产而不是问题**：本次 7 个缺陷里有 2 个正是靠分歧发现的。
  报告里遇到分歧会显式标注 `⚠️ 根因定位分歧`，把双方的依据并列展示。
